# 什麼是 TCP / UDP

TCP = Transmission Control Protocol（傳輸控制協定）  
UDP = User Datagram Protocol（使用者資料報協定）

## 一句話差異

- TCP：可靠、保序、連線導向，適合「資料正確性」優先。
- UDP：無連線、低開銷、不保證到達與順序，適合「低延遲」優先。

## 快速比較

| 項目          | TCP                         | UDP                |
| ------------- | --------------------------- | ------------------ |
| 連線模式      | 連線導向（3-way handshake） | 無連線             |
| 可靠性        | 有（ACK、重傳、保序）       | 無內建保證         |
| 傳輸單位      | Byte stream（位元組流）     | Datagram（資料報） |
| 順序保證      | 有                          | 無                 |
| 流量/壅塞控制 | 有                          | 無（需應用層自管） |
| Header 開銷   | 較高                        | 較低               |
| 延遲          | 相對較高                    | 相對較低           |
| 適合場景      | 正確性優先                  | 即時性優先         |

## 傳輸單位差異（這題很常被問）

- TCP 的 `Byte stream`（位元組流）：
  - TCP 只保證「位元組順序正確」，不保證你在應用層送出的每一筆資料邊界。
  - 對接收端來說，拿到的是一條連續資料流，可能發生：
    - 你 `send` 兩次，對方一次 `recv` 就全拿到（合併）
    - 你 `send` 一次，對方要 `recv` 多次才拿完（拆分）
  - 所以應用層通常要自己定義 framing（例如固定長度 header、分隔符、length-prefix）。
- UDP 的 `Datagram`（資料報）：
  - 以「一個 datagram = 一則訊息」為單位傳送，保留訊息邊界。
  - 一次 `sendto` 對應一個 datagram；接收端一次 `recvfrom` 讀一個 datagram。
  - 若 datagram 太大超過路徑可承載大小，可能被 IP 分片或直接丟棄（依情境與設備而異），因此實務上會控制封包大小。

### 面試一句話

- TCP 是 byte-stream（保序但不保訊息邊界）；UDP 是 datagram（保訊息邊界但不保可靠到達）。

## 什麼時候用 TCP

- 網頁與 API（HTTP/1.1、HTTP/2、HTTPS）
- 檔案傳輸（FTP、SFTP）
- 郵件（SMTP、IMAP、POP3）
- 遠端連線（SSH）

理由：不能亂序、不能漏資料，寧可多一些延遲也要正確。

## 什麼時候用 UDP

- 即時語音/視訊
- 線上遊戲即時狀態同步
- DNS 查詢（典型短請求）
- 串流與即時通訊協定（常在應用層自行補機制）

理由：部分封包遺失可接受，但延遲和抖動要低。

## 常見誤解

- 「UDP 一定比較快」：不一定。  
  在高丟包場景，若應用層補太多重傳，體感不一定比 TCP 好。
- 「TCP 一定很慢」：不一定。  
  現代網路下 TCP 對多數 Web 場景仍非常有效率。
- 「UDP 不可靠所以不能用」：錯。  
  很多即時應用就是要用 UDP，再在應用層做選擇性保證。

## 面試可背版

TCP 重可靠與順序，UDP 重低延遲與低開銷。  
如果你的需求是「資料不能錯、不能漏、不能亂序」，用 TCP；  
如果是「即時互動、偶爾掉包可接受」，通常選 UDP（並在應用層補策略）。
